[01]这是什么 What this is about

先搞清楚「镜像」在这里到底指什么What an "image" actually is in this context

PS5 越狱环境里，游戏备份有五种形态，其中前三种是你实际会用到的。ShadowMountPlus 会自动扫描并挂载它们，但适用场景并不相同：

ShadowMountPlus handles five kinds of game backups. The first three are the ones you will actually use — they are not interchangeable.

那为什么要费劲把文件夹「打成镜像」？两个原因：

  • 单个文件更好搬——几万个碎文件的目录，用 Finder 复制容易中断、容易带出 macOS 垃圾文件，也没法整体校验完整性。
  • 挂载方式不一样——某些游戏只有在被当作「外置盘内容」时才能正常跑，镜像正好提供这个语义。
Two reasons: a single file is far easier to move and verify than tens of thousands of loose files, and some titles only behave correctly when they are handled as external-drive content.
[!] 先说结论：默认选 .ffpkg，只有一种情况选 .exfat

ShadowMountPlus 官方把 UFS（.ffpkg）列为推荐格式，把 .exfat 定位成「给那些不按外置盘方式处理就跑不正常的游戏用」。

所以本站的主线是：先做 .ffpkg；只有当某个游戏确实异常时，才为它改做 .exfat。第 03 节有完整的判断表和一个交互决策器。

3.4另外两种实验性格式 The two experimental formats

ShadowMountPlus 实际支持五种形态，上面只覆盖了你会用到的三种。剩下两种围绕 PFS（PlayStation FileSystem，索尼自家的文件系统），官方都标着 Experimental。

Two more formats exist, both PFS-based and both marked Experimental. They are not a "better version" of .ffpkg — they trade speed for space.
扩展名内部文件系统挂载后端官方状态压缩
.ffpkgUFS2LVD 或 MD（可配）Recommended无
.exfatexFATLVD 或 MD（可配）兼容场景无
.ffpfsPFS仅 LVDExperimental无
.ffpfscPFS 容器仅 LVDExperimentalzLib

默认扇区大小也不一样：UFS 是 4096、PFS 是 32768、exFAT 是 512。

.ffpfsc 用起来有三个硬性限制：

  • 它只能当「外壳」。官方原话："Compressed PFS mode is intended only for nested images." 并明确要求 "Do not place game files directly in the container root." 打包时数据会被零填充到 64 KB 扇区边界，所以它天生是个容器——里面要套另一个镜像，官方推荐套 exFAT 镜像。
  • 它会明显降速，这是最重要的取舍。解压虽然由硬件加速，但吞吐只有约 150–250 MB/s。官方说这大约是外置 USB / FFPKG / exFAT 镜像的 1/3，是内置盘速度的约 1/10。「大量读取数据或持续流式加载贴图」的游戏会卡顿，官方建议挑游戏来压。
  • 直接把文件夹打成 PFS 有个已知坑。启用压缩时镜像能建好、校验也能过，但主机读取文件是错误的。官方说这个高级选项「对游戏备份没有实际好处」，让用默认的 exFAT 包裹布局。
[i] 为什么它只能这么慢：PS5 的硬件解压只认两种算法

PS5 的 I/O 复合体里有一颗专用硬件解压单元，但它只支持 zlib 和 Oodle Kraken 两种算法。所以 .ffpfsc 用 zLib 并不是「选型保守」，而是被主机硬件约束死的——换成别的算法，主机的硬件解压路径根本解不了，只能退回 CPU 软解，而游戏资源是流式加载的，这条路走不通。

偏偏 zlib 是这颗芯片上的慢路径：官方实测 .ffpfsc 解压只有 150–250 MB/s，而同一颗单元跑 Kraken 能输出 8–9 GB/s（压缩得特别好的数据最高 22 GB/s）——差了 40 倍以上。

Kraken 之所以能做到又快又小（比 zlib 压缩比高 29%、解压快约 4 倍），是因为它按整块解码设计，不像 zlib 那样逐位串行解析——这让它无分支、可并行，才有可能做进硬件。

制作这两种格式要用 PSBrew/MkPFS（GPL-3.0，Python，Windows / macOS / Linux 都支持，Apple Silicon 是明确支持路径）。它的默认输出就是官方认为最稳的「exFAT 包在压缩 PFS 里」布局：

bashMkPFS 基本用法，macOS 同样适用
# 安装（带 GUI）
python3 -m pip install -U "mkpfs[gui]"

# 游戏目录 → .ffpfsc（默认 exFAT 包裹，官方称最稳的压缩布局）
python3 -m mkpfs pack folder './PPSA12345-app' './PPSA12345.ffpfsc'

# 已有镜像 → .ffpfsc
python3 -m mkpfs pack file './PPSA12345.exfat' './PPSA12345.ffpfsc'

# 未压缩的直接 PFS
python3 -m mkpfs pack folder --raw './PPSA12345-app/' './PPSA12345.ffpfs'

# 反向解包
python3 -m mkpfs unpack --deep './PPSA12345.ffpfsc' './out/'
[!] 结论：除非你明确要省空间，否则别碰这两种

.ffpkg 官方推荐、速度快、一条命令做好。.ffpfsc 唯一的优势是省空间，代价是约 1/10 的内置盘读取速度，而且官方还标着实验性。

适合压的是体积大、但读取强度低的游戏（老游戏、剧情向）；需要持续读盘的 3A 大作不要压。另外 --block-size 默认 65536，小文件多的目录会产生块对齐浪费，极端情况下镜像比源还大——官方建议改用两遍法或降到 16384/32768。

4.1确认源目录结构正确 Check the source layout

这是最容易踩的坑：游戏文件必须直接在目录根下，不能多套一层。ShadowMountPlus 靠根目录的 eboot.bin 和 sce_sys/param.json 来识别游戏。

The most common mistake. eboot.bin must sit at the root of the source folder — no extra nesting level.
// 正确 Correct PPSA12345/ ├── eboot.bin ← 必须在根下 ├── sce_sys/ │ └── param.json ← 必须在 ├── prx/ ├── sce_module/ └── ampr_emu.index ← 有就保留
// 错误 Wrong PPSA12345/ └── PPSA12345-app0/ ← 多了一层 ├── eboot.bin └── sce_sys/ 多套一层会导致 PS5 识别不到游戏。
bash先看一眼你的目录长什么样
$ GAME="/Volumes/MYSSD/downloads/ps5/PPSA12345"
$ ls -la "$GAME"
$ ls "$GAME/eboot.bin" "$GAME/sce_sys/param.json"   # 两个都必须存在

4.2确认磁盘空间够用 Check free space

镜像都会比游戏本身大一点，具体差多少取决于格式：

  • .ffpkg（UFS2）：元数据开销小，一般多预留 几百 MB 就够。
  • .exfat：每个文件都会按 64 KiB 簇向上取整，零碎文件多的游戏会明显变大，建议多预留 1–2 GB。
  • 源目录和镜像在同一块盘上（最常见的做法）时，需要大约两倍的可用空间。
If the source folder and the image live on the same volume — the usual case — budget roughly 2 × the game size free. UFS2 adds far less overhead than exFAT.

[i] 别搞混「两块 M.2」

M.2 插进 PS5 主机的扩展槽 → 走 /mnt/ext1/；M.2 装进硬盘盒当 USB 外接用 → 走 /mnt/usb0/。两者路径完全不同。

外置盘根目录（内置盘与 M.2 结构一样，只是挂载点不同） MYSSD/ └── homebrew/ ├── PPSA12345.ffpkg ← UFS2 镜像 ├── PPSA67890.exfat ← exFAT 镜像 └── PPSA11111/ ← 也可以放文件夹格式 ├── eboot.bin └── sce_sys/
[X] 三个常见错误

1. 把镜像放进了子文件夹（如 homebrew/ps5/PPSA12345.ffpkg）——默认只扫描第一层。
2. 目录名写成了 hombrew、Homebrew 等——大小写和拼写都要对。
3. 外置盘本身没格式化成 exFAT——普通 exFAT 盘就行，不需要格成 PS5 专用扩展存储。

5.2文件怎么进到内置盘 / M.2 里 Getting files onto internal storage

外置盘可以在 Mac 上直接拷，但主机自带硬盘和 M.2 都不行——它们由 PS5 用自己的独占格式管理，Mac 根本读不了。所以顺序是反过来的：

  1. 先把 M.2 装进 PS5 并由主机格式化：设置 → 存储 → M.2 SSD → 格式化。没做过这一步，/mnt/ext1 根本不存在。
  2. 越狱并加载 payload（Kstuff + ShadowMountPlus）。etaHEN 这类环境通常自带 FTP 服务。
  3. 把镜像传进目标目录——两条路选一条：
方法怎么做适合
FTP 直传 在 Mac 上用 FileZilla / Cyberduck 连 PS5 的 FTP，传到 /mnt/ext1/homebrew/ 方便，但走网络；200 GB 要传很久，务必用支持断点续传的客户端
U 盘中转 先在 Mac 上拷到 USB 盘 → 插到 PS5 → 用文件管理器类 homebrew 把它移到 /mnt/ext1/homebrew/ 大文件更快（USB 3 直拷）；代价是要挪两次

Both the console storage and the M.2 are managed by the PS5's own format, so you cannot pre-load them from a Mac. Install and format the M.2 in the console first, then transfer over FTP or via a USB drive.

[X] M.2 三个常见错误

1. 没在 PS5 上格式化过 M.2——/mnt/ext1 不存在，传了也没用。
2. 传到了 /mnt/ext1/ 根目录，而不是 homebrew/ 子目录。
3. 把「M.2 插在主机里」和「M.2 装在硬盘盒里」搞混——前者是 /mnt/ext1/，后者是 /mnt/usb0/。

5.4确认挂载成功 Confirm the mount

  • 屏幕上会出现一张 toast 通知，提示发现并挂载了镜像。
  • 回到 PS5 主界面，游戏会出现在游戏库里，图标和标题正常显示。
  • 首次挂载有一个 stability_wait_seconds（默认 10 秒）的等待期——这是设计如此，别急着拔盘。
[i] 排查的话，先打开调试日志

ShadowMountPlus 默认 debug=1，日志写在 PS5 的 /data/shadowmount/debug.log。挂载失败的原因基本都能在里面看到。配置文件在 /data/shadowmount/config.ini，第一次启动时会从模板自动生成。

[!] 官方提醒：在内置盘上挂载镜像风险更高

ShadowMountPlus 的 README 开头就写着：

Warning! Mounting images can cause shutdown problems and data corruption on internal drives! This depends on many factors, but is more common with older firmware versions.

也就是说内置存储（主机盘和 M.2）比外置盘更容易出问题，老固件尤其明显。好消息是缓解手段默认就开着：mount_read_only=1 的默认值就是 1，镜像默认只读挂载——别去关它。老固件上先用不重要的游戏试，重要数据务必先备份。

5.5APR-Emu 类型的游戏 APR-Emu titles

有一类游戏做过资产重打包——原本散在 /app0 里的资源被换成了自定义的压缩包格式（项目是 drakmor/ampr_emu，和 ShadowMountPlus 同一个作者，内部用 LZ4 压缩、由游戏自己的运行时解码）。判断方法很简单：游戏目录里有 ampr_emu.index。

这类游戏有两条硬性要求。第一条是：下面这些东西必须作为一个整体一起部署，少一个都加载不了。

文件作用运行时需要吗

[X] 两条最容易踩的

1. ampr_emu.index 与游戏版本强绑定。它依赖索引记录里的 fileId——把 A 版本的索引配 B 版本的游戏文件，运行时会报 fileId 与路径对不上。所以做镜像时整个目录一起打包，不要从别处混入文件。

2. 卷少一个就加载不了。清单里点名的 .pak 必须全部在位；复制中断、或者只挑了「看起来大的」几个卷，都会导致清单校验失败。

If the game folder contains ampr_emu.index, it uses drakmor's ampr_emu asset packs. The index, the assets manifest, its .runtime sidecar and every .pak volume must be deployed together — the runtime verifies build IDs, so mixing files from different builds breaks manifest loading.

[07]原理对比 Under the hood

想知道为什么两条路差这么多，看这一节Why the two routes differ so much

7.1两种文件系统的性格 Two very different filesystems

exFATUFS2
出身为移动存储设计的通用交换格式FreeBSD 的经典 Unix 文件系统
元数据简单：一份 FAT 表 + 分配位图完整：超级块、柱面组、inode 表、块位图
小文件效率每个文件至少占满一个簇，浪费多fragment 级别分配，浪费少
macOS 支持原生读写，靠 FSKit 用户态实现不能原生挂载，只能用工具读写
PS5 原生不是是——PS5 内部就用 UFS

7.2为什么做镜像的方式差这么多 Why the build flow differs so much

因为 macOS 能原生挂载 exFAT，但不能原生挂载 UFS2。这直接决定了两条完全不同的技术路线：

  • exFAT 路线：先建一个空白镜像 → 格式化成 exFAT → 挂载到系统 → 用普通文件复制的方式把游戏写进去 → 卸载。
    代价是「写入过程由 macOS 的文件系统驱动参与」，所以会带出 ._* 影子文件、.fseventsd 这类 macOS 私有产物，必须手工清理。
  • UFS2 路线：UFS2Tool 直接按字节构造整个文件系统，自己管理 superblock、inode、位图。
    不经过 macOS 的文件系统层，所以根本不会产生任何 macOS 残留，也不需要挂载和卸载。
macOS can mount exFAT natively but not UFS2. That single fact shapes both routes: the exFAT path writes through the macOS filesystem driver (hence the AppleDouble and .fseventsd cleanup), while UFS2Tool writes the filesystem structure itself, byte by byte, bypassing the OS entirely.

7.3那为什么还要保留 exFAT 这条路 So why keep the exFAT route at all

三个理由：

  • 兼容性兜底——确实有一批游戏只有在被当成「外置盘内容」时才正常，这是官方给 exFAT 的唯一用途定位。
  • 零依赖——全部用 macOS 自带命令，不需要下载任何第三方工具。
  • 可手工修改——exFAT 镜像能挂载后直接用 Finder 改内容；UFS2 只能靠 UFS2Tool 的 add/delete/replace。
